# ReportDesk 医院内网 Web 与 IIS 实施方案

版本：讨论稿 v1.0；日期：2026-09-18；代码基线：`e54c88ffc6416911eaf6e3a62729b057b2a05552`（桌面版 v0.3.0）。

## 1. 目标与当前阶段

将现有 ReportDesk 改造成浏览器可访问的集中报表查询系统，部署到医院内网 IIS。保留原 HIS 中编辑、保存和“一键发布”的工作方式，由 ReportDesk 读取已发布报表，统一提供查询和 Excel 下载。

本次用户要求是生成可跨电脑交接的方案；本包不代表已开始编写 Web 功能、已部署服务器或已取得生产系统变更授权。

## 5. 第一版架构

```text
原 HIS 管理员编辑并发布
          │
          ▼
Oracle：系统发布表及文件内容
          │ 只读获取发布元数据及报表文件
          ▼
ReportDesk 同步模块 ──→ 校验后的本地报表版本
                              │
医院浏览器 ── HTTPS ── IIS / ReportDesk.Web
                              ├─ 查询任务和进度
                              ├─ 按会话隔离结果
                              ├─ Excel 下载
                              └─ 只读查询 Oracle 业务数据
```

建议新增 `src/ReportDesk.Web/`，由同一站点提供静态页面与 API。第一版使用单服务器、单工作进程；复用业务代码，不为每个浏览器启动桌面 Host 子进程。

共享 Core 可采用多目标框架或提取独立共享库，保留 net48 桌面版。选择由兼容性验证结果决定，避免复制两套 SQL 和导出规则长期分叉。

暂不引入多服务器、Redis、微服务或完整管理后台。同步状态、报表版本、任务最小元数据持久化到站点公开目录之外；存储实现选择需考虑原子写入和回滚，可采用轻量本地存储。

## 6. HIS 发布同步

### 6.1 已查明的来源

- `HIS.SYS_UPDATE_RELEASE`：发布编号、操作时间、发布说明等。
- `HIS.SYS_UPDATE_RELEASE_FILE`：文件编号、发布编号、文件名、相对路径、目录标志、`CONTENT` BLOB。
- 报表“一键发布”会读取主表显示 XML、查询定义 XML，以及存在时的明细显示 XML，压缩保存。
- 原 HIS 客户端在程序启动路径读取新发布、解压，再更新本地文件。仅注销登录是否触发同一路径未确认。

完整证据见 [发布机制说明](03-HIS发布机制证据.md)。ReportDesk 只读取已有发布，不调用原 SaveRelease，不修改原发布表和 HIS 配置。

### 6.2 第一次导入

从一台已完成更新且没有未发布编辑的客户端取得完整报表基线，保留相对目录及配套文件。不能假设发布表保留了系统最初安装以来的全部文件。

记录基线文件清单与内容哈希。导入过程中记录起始发布范围并补取期间的已提交更新，重复读取应幂等，不能简单把“导入结束时最大 ID”设为游标而跳过期间发布。

### 6.3 后续同步算法要求

1. 仅一个同步工作者执行，避免两个轮询同时修改当前版本。
2. 查询已提交发布元数据，筛选报表相关文件；系统表还可能包含 DLL、EXE、整目录更新，不能一概下载执行。
3. 发布 ID、文件 ID 和内容哈希组成可追踪记录。不要只依赖 `VERSION` 或 `FILECOUNT`。
4. 不直接照搬原代码的“ID 和时间都大于游标”作为唯一增量条件：并发事务可能产生较小 ID 晚提交的情况。设计重叠回查、幂等处理和周期性元数据核对，验证不会漏更新。
5. 单文件 BLOB 是 ZIP 内容，内部条目名可能为空；实际输出名称取可信化后的数据库路径和文件名。拒绝越界路径、绝对路径、目录穿越；限制解压大小，禁用 XML 外部实体。
6. 在独立 staging 目录读取并验证同次发布的相关文件，再生成可用版本，原子切换。新版本未完成前继续使用上一版。
7. 失败记录、成功应用记录与扫描进度分开保存，失败发布必须可重试且不能因游标推进被永久跳过。
8. 进程启动时补查，运行期间按建议 30 秒轮询；无更新仅查元数据，不重复读取 BLOB。检查失败采用退避并记录脱敏错误。
9. 原子保存状态；崩溃或重启后恢复。同步模块无权限执行 HIS 更新包中的程序。

原发布表没有已确认的“报表删除”语义。不得把某次发布里没有出现的文件当成应删除；新增报表识别、菜单资源与文件的对应关系、历史清理影响需在实现中单独核实。

### 6.4 IIS 生命周期

建议第一版同步模块与 Web 应用同进程，设置应用池 AlwaysRunning、站点预加载和适当的空闲配置，处理回收后的补查。即便如此也不承诺全天精确每 30 秒执行。

若以后要求无人访问、IIS 回收或网站维护期间仍持续同步，应改为独立 Windows 服务或受管理的后台任务；不要把关键同步仅绑定到某个浏览器页面的计时器。

### 6.5 页面与版本关系

| 情况 | 行为 |
| --- | --- |
| 新开页面 | 使用最近一次成功同步的报表版本 |
| 填条件期间定义变化 | 查询提交携带定义版本；不匹配时提示刷新，保留兼容输入，不静默套新定义 |
| 查询已经执行 | 固定启动时的报表版本和参数完成 |
| 已显示结果导出 | 基于该次结果及筛选排序快照导出，不重新按新版 SQL 查询 |
| 同步失败 | 保留上一版，显示最后成功同步时间及异常状态，不冒充最新 |

## 7. 无登录与全院数据

不建立应用用户、角色或科室权限系统。所有人可见同一报表目录，可查询全院各科室。

科室仍可作为业务筛选条件。尊重每张原报表的绑定方式；“全部科室”只使用已确认的 SQL 含义，不能通过删除条件实现全院查询。遇到当前操作员、当前角色等隐含身份参数，需逐项确定适配规则；没有身份时不伪造 admin，也不自动丢弃限制。

无登录不等于共享会话。服务端分配不可预测的匿名会话标识，用 HttpOnly、Secure 等合适属性的 Cookie 维持；每个标签页可以有独立任务 ID。所有任务、分页、筛选、取消、导出接口都校验所属会话，防止任务结果串用。清空 Cookie 或结果过期后明确提示重新查询。

网站限定院内网络访问，数据库凭据、任意 SQL 执行、任意服务器路径读写和发布管理功能不开放给浏览器。接口使用报表 ID、定义版本和参数，不接受用户上传任意 SQL。按实际请求方式实现防跨站请求保护。

日志可以记录时间、IP、匿名会话、报表 ID/版本、任务状态、耗时和导出状态，但不能据此断言具体操作人身份。不记录密码、连接串、患者明细、完整结果或未经处理的 SQL/参数值。

## 8. 查询、导出和容量

第一版支持报表搜索、条件与字典选项、查询进度、取消、结果分页、筛选排序和 Excel 下载。特殊交叉表、模板计算和打印版式按现有支持能力逐项标识，不因成功下载 XML 就宣称完整支持全部 HIS 功能。

查询使用任务模式：提交后返回任务 ID，后台受控执行，页面轮询状态与结果；避免把大查询绑定在一个长时间 HTTP 请求上。

建议任务状态：Queued、Running、Succeeded、Failed、Cancelled、Interrupted、Expired。执行并发、队列容量、结果内存预算、磁盘临时空间和导出并发分别控制，具体值由测试决定。

不偷偷增加固定查询行数上限或截断结果。资源不足时明确排队/拒绝/失败；若后续需要调整超时或数据范围规则，单独说明业务影响。大结果评估落盘或流式导出，不能无限保留所有人的 DataTable。

取消需传到 Oracle 执行，现场验证服务器端是否实际终止；页面显示“已请求取消”不等于已停止数据库工作。断网、页面关闭不应无限泄漏任务和连接。

IIS 回收时进行中的任务明确标为 Interrupted，不自动重复执行整院大查询。保留最小任务元数据以便恢复后解释状态，结果是否仍可下载按其存储及过期策略判断。

初始验收目标是 50 个并发浏览会话和合理的查询混合负载，不是无条件 50 个全院大查询同时执行。用代表性短、中、大报表测量端到端耗时、队列等待、CPU、峰值内存、Oracle 会话和取消效果，再锁定部署参数。

## 9. 部署与回滚

建议目录（只是规划，不要求目标电脑有相同盘符）：

```text
D:\Apps\ReportDesk\releases\<应用版本>\   Web 发布产物
D:\ReportDeskData\Reports\versions\     报表版本
D:\ReportDeskData\Reports\staging\      同步暂存
D:\ReportDeskData\State\                同步与任务状态
D:\ReportDeskData\Results\              临时查询/导出文件
D:\ReportDeskData\Logs\                 脱敏日志
D:\ReportDeskData\Backups\              配置与版本备份
```

实施步骤：

1. 运行环境只读检查，确认系统补丁、已有 IIS 网站和绑定、.NET 运行时、硬件和磁盘。确认目标机器能连接 Oracle。
2. 开发电脑完成构建和验证，制作 x64 发布包、校验值、离线依赖清单和版本记录。生产服务器不安装开发工具链作为运行前提。
3. 在维护窗口安装匹配的 .NET Hosting Bundle；该组件可能需要 IIS 重启，必须评估现有网站影响。
4. 建独立站点、独立应用池；ASP.NET Core 使用 No Managed Code，x64 发布关闭 32 位应用。建议单工作进程，并配置预加载与重启补查。
5. 确定域名、端口、HTTPS 证书和仅内网访问规则。不抢占已有 HIS 绑定，不以管理员身份运行应用池。
6. 应用目录原则上只读；数据、状态和临时目录给应用身份所需写权限。数据目录不映射成公开静态目录。
7. 由现场安全配置 Oracle 连接和只读权限；桌面用户 DPAPI 密文不跨机器沿用。保护服务器凭据及密钥，建立对应恢复方式，不写入交接文件或 Git。
8. 导入初始报表，完成发布同步、查询导出和容量验收，才转入正式使用。

以上 IIS 配置依据 [微软部署说明](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/iis/?view=aspnetcore-10.0)；Hosting Bundle 的安装及重启要求见 [微软说明](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/iis/hosting-bundle?view=aspnetcore-10.0)。

Web 项目完成后，预期发布命令示例（当前没有这个项目，不能现在执行）：

```powershell
dotnet publish .\src\ReportDesk.Web\ReportDesk.Web.csproj -c Release -r win-x64 --self-contained false -o .\artifacts\web\win-x64
```

回滚分两类：应用故障切回上一版本发布目录；报表更新故障恢复上一份已验证报表及匹配的同步状态。报表回滚要暂停自动重试或隔离对应失败发布，避免马上再次应用同一问题版本。两者都不回写 HIS，不回滚 Oracle 业务数据。

| A10 | 50 会话混合负载下记录资源和时延，确认并发/队列/过期参数，不只测试静态页面访问 |
| A11 | 服务器未暴露配置、凭据、HIS 文件路径或任意 SQL 接口；临时结果到期清理 |
